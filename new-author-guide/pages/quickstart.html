Step 1 / Submit Workshop Request

Submit Workshop Request

Start in WMS

Submit the request before development starts

  1. Connect to Corporate VPN, open Oracle Workshop Management System, and click Submit a New Workshop Request. Open WMS Requires Oracle VPN and WMS access.
  2. Complete Workshop Basic Information thoroughly. The fields that matter most at this stage are Stakeholder, Workshop Council, Workshop Owner Group, Workshop Abstract, Workshop Outline, and Workshop Prerequisites. Follow the field placeholders, open the ? tooltips for detail, or use the Prompt examples generator below, then copy each result into its matching WMS field.
  3. Open Tags and set the required tag groups before you click Create: one Level, at least one Role, at least one Focus Area, and at least one Product.
  4. Use Go to Market - Social while the workshop is still early if blog, social, video script, or promotional media details will be needed later in the publish flow.
  5. Wait for council review after submission. Council review normally takes 2 to 3 business days; if nothing changes after 3 business days, use Message the Team or find council contacts under People & Role Reports > Workshop Council Members.

Before you move on

What you should know before moving on

  • The title, abstract, outline, and prerequisites tell a reviewer exactly what the workshop will accomplish.
  • Stakeholder, council, owner group, and required tags are already correct in WMS.
  • Check the WMS status before starting development. If the request is still in council review, wait for feedback or approval; begin development only after the initial WMS review gate clears.
  • You understand that later Self Quality Assurance, stakeholder review, and Quarterly Quality Assurance all reuse this same WMS record.
Watch for

Common first-step mistakes

  • Writing a vague abstract that forces the council to ask for more information.
  • Starting content development before the request is aligned with the real workshop idea.
  • Leaving tags, stakeholder ownership, or later publish requirements until the end of the flow.

Step 2 / Workshop authoring

Create Workshop

Choose an authoring path

Create the workshop with NoDoc or GitHub

NoDoc is the recommended default. The existing GitHub process remains available as the second path.

Recommended path

Build a reviewer-ready NoDoc article

Use No Doc Repo to turn the approved workshop idea into a structured article, then prepare the same content for preview and WMS review.

  1. Create the article shell. Sign in with Oracle SSO, confirm your author or reviewer role, choose the Focus Area, and create the article version in No Doc Repo.
  2. Build the page set. Add the Prepare, Author, and Review pages in order, then apply the required metadata and structured content.
  3. Review the change. Use comments, drafts, and Difference to keep revisions intentional and technically accurate.
  4. Prepare the handoff. Preview the saved page set, verify links and page order, and record the NoDoc preview evidence in WMS.

Fork, clone, sync

Build the repository in the same order the canonical guide expects

Keep production, your fork, and your local clone clearly separated. New authoring gets much harder when those roles blur.

  1. Fork the repository. A fork is your personal GitHub copy of the official Oracle LiveLabs repository. Make changes in your fork before submitting them back to the official repository.
  2. Clone your fork. A clone is the copy on your laptop. Use GitHub Desktop and select To contribute to the parent project when prompted so upstream/main stays connected.
  3. Sync with upstream/main. upstream/main is the official Oracle LiveLabs source. Before editing each day, click Fetch origin, then open Branch > Merge into Current Branch and merge upstream/main into main.
  4. After the merge succeeds, click Push origin so your local clone and your fork stay aligned before you author anything new.
  5. Copy the sample workshop structure from common/sample-livelabs-templates/sample-workshop, keep every file and folder lowercase, and point manifest.json at real markdown files instead of placeholders.
Preview checkpoint

Publish the preview checkpoint

Use GitHub Pages to prove the workshop path works before deep writing starts.

  1. Open settings. In your fork, open Settings > Pages.
  2. Select source. Choose the main branch and save.
  3. Wait for publish. Let GitHub Pages finish publishing before testing the link.
  4. Open the exact variant. Test the workshop URL you plan to share, including ?qa=true.
  5. Keep checking both previews. Use local preview while editing, then confirm the same path works on your personal github.io site.
Commands and baseline

Group GitHub commands by the job they perform

Copy only the command group you need. Keep setup, synchronization, and manifest baseline work separate so review problems are easier to diagnose.

Git settings

Configure paths and filename case

Run this once on a workstation before you work with long paths or case-sensitive filenames.

git config --global core.longpaths true
git config --global core.ignorecase false
Repository synchronization

Sync your fork before editing

Use this group before a new authoring session so your fork and local clone start from the current upstream branch.

git remote -v
git fetch upstream
git merge upstream/main -m "Sync with main"
git push origin main
Manifest baseline

Start with a minimal manifest

The manifest drives workshop navigation. Each tutorials entry should point to a real markdown file in your workshop folder; if a filename is wrong, the lab may appear blank or fail to load.

{
  "workshoptitle": "My Workshop Title",
  "help": "my-team@oracle.com",
  "tutorials": [
    {
      "title": "Introduction",
      "filename": "./../../introduction/introduction.md"
    },
    {
      "title": "Lab 1: Build the environment",
      "filename": "./../../1-build-environment/1-build-environment.md"
    }
  ]
}
workshoptitle

Replace with the real workshop title from WMS.

help

Replace with the correct support email or team alias.

tutorials.title

Replace with the visible lab or task titles authors should see in the left navigation.

tutorials.filename

Replace with the relative path to each real markdown file.

Lab entries

Add or remove entries so the manifest matches the actual number of labs.

Before you move on

Step 2 exit criteria

  • GitHub Desktop, Visual Studio Code, and Live Server are installed and working with the Oracle-linked GitHub account.
  • The target repository and common are both forked or available, and the local clone still points to upstream/main.
  • Folder names, file names, and manifest paths are lowercase and case-correct.
  • Your personal GitHub Pages URL renders the same workshop path you intend to share for review.
Watch for

Common build-stage mistakes

  • Using the wrong GitHub account or cloning the wrong repository before the workshop path is confirmed.
  • Skipping the daily upstream merge and only discovering conflicts or stale templates at pull request time.
  • Leaving sample manifest fields, mixed-case filenames, or broken tutorial paths behind.

Step 3 / Quality Assurance and release

Review & Publish

Complete Self Quality Assurance in order, fix pull request blockers by class, and submit publishing details only when the workshop is production-ready.

Self Quality Assurance order

Save the checklist before the final handoff

Complete Self Quality Assurance in order, save evidence, and submit publishing details only when the workshop is production-ready.

  1. Open the review URL, append ?qa=true, and run the workshop end to end.
  2. Open the approved NoDoc preview and run the article end to end.
  3. Update WMS title, descriptions, outline, prerequisites, tags, and Development GitHub/GitLab URL to match the workshop reviewers will open.
  4. Confirm the WMS details, NoDoc article structure, metadata, preview, and ownership match the workshop reviewers will open.
  5. Open Self Quality Assurance Checklist, check every required box, and upload the requested evidence.
  6. Add the pull request link and personal github.io preview link to the checklist.
  7. Add the NoDoc preview and article handoff evidence to the checklist.
  8. Click Save first. Then move to Self Quality Assurance Complete and certify the change.
  9. Stakeholders verify the workshop and move it to Completed before publishing.
Pull request checks

Fix review blockers by class instead of guessing

When the pull request shows a red X, name the failing workflow first. Image-size problems, markdown-structure problems, and publishing metadata problems are different repairs.

  1. If the pull request fails LiveLabs Image Validation, use OptiShot to resize the blocking image to 1280px or less in either dimension, then commit the updated image and rerun the checks.
  2. If the pull request fails LiveLabs Markdown Validation, fix the exact file and rule: required sections, task format, alt text, filename case, copy tags, or inline HTML.
  3. Use the local validator when you want faster repair loops than waiting for GitHub Actions after every commit.
Publish handoff

Move the approved GitHub change into publishing

Keep preview and production URLs separate.

  1. Create the pull request from GitHub Desktop after the Quality Assurance fixes are pushed, and include the WMS ID in the pull request title because review will not start without it.
  2. On the pull request page, fill the required checklist and general requirements from the Quality Assurance handoff so reviewers can tell the workshop is ready for merge.
  3. Confirm the branch is up to date with main and has no merge conflicts before you request approval.
  4. Open WMS > Publishing, click Publish to LiveLabs, set the publish type and workshop time, and replace any personal preview URL with the final oracle-livelabs production path.
  5. After merge and publishing approval, verify the production workshop and leave WMS aligned for the next Quarterly Quality Assurance cycle.
Publish handoff

Move the approved NoDoc article into release review

Use the NoDoc preview and WMS record as the release evidence.

  1. Confirm the article version, page order, metadata, links, code, and preview are correct in NoDoc.
  2. Save the Self Quality Assurance checklist with the NoDoc preview, ownership, and approval evidence.
  3. Update the WMS Publishing details and request the release handoff only after stakeholder approval.
  4. Verify the published workshop and keep the WMS record ready for Quarterly Quality Assurance.

Before you move on

Step 3 exit criteria

  • The preview works end to end with ?qa=true, and the WMS metadata matches the workshop.
  • The NoDoc preview works end to end, and the WMS metadata matches the workshop.
  • The Self Quality Assurance checklist is saved before any status change and stakeholder verification has a clear handoff.
  • The pull request title includes the WMS ID, the branch is current, and any failing check class is understood.
  • The NoDoc article, preview, owner, and approval evidence are ready for release review.
  • The Publishing tab uses oracle-livelabs production URLs, not the personal preview link.
  • The WMS Publishing details point to the approved production location.
  • The production workshop is verified, and WMS stays accurate for Quarterly Quality Assurance.
Watch for

Common release-stage mistakes

  • Sharing a preview before checking tutorial order, links, images, and copy flows end to end.
  • Changing WMS status before the checklist is saved and certified.
  • Mixing development and production URLs or opening a pull request from a stale branch.
  • Publishing a NoDoc article before the preview, ownership, and stakeholder approval are recorded.
